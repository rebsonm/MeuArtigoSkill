## Verified connected search capability

The available Google Drive connected \`search\` action supports
\`special_filter_query_str\`, \`item_type="folder"\`, and an opaque
\`page_token\`/returned \`next_page_token\` on provider-owned metadata pages.
The folder name must be obtained and checked from real provider observations.
An independently requested \`get_file_metadata\` confirms exact item ID,
folder MIME type, and parent IDs.

Read-only probe performed during F6:
- Scope: the previously provisioned isolated test project named
  \`MEU_ARTIGO_PR74_TESTE_SINTETICO_...\`, not a scientific corpus.
- Exact parent-scoped query: \`'<SYNTHETIC_PROJECT_ROOT_ID>' in parents and trashed = false\`.
- Folder-only search: **1 page**, **1 folder** with name \`01_Dados\`;
  the response did not return another page token.
- Separate metadata: folder MIME type and expected parent ID both confirmed.
- Provider object mutations: **0**.
- No need to publish the actual private Drive resource IDs in the repository.
- Evidence is a real provider lookup but not a locally verified
  \`scripts/drive_api_proof.py\` / \`drive_f5_operator.py\` OAuth run.

Crucial limitation: \`item_type="folder"\` **filters out nonfolder items**.
Even a full, terminal folder-only search cannot prove no same-named file,
shortcut or unsupported MIME item exists. \`list_folder(top_k)\` also does not
provide an authoritative all-types pagination receipt.
A missing folder in this view does **NOT** authorize folder creation.
Do not convert this folder-only response into the all-types
\`page_evidence\` consumed by \`drive_create_guard.py\`.

## Assistant-built fail-closed bridge

The new helper \`scripts/drive_f6_connected_search.py\` validates a host-supplied
transcript of folder-only search pages:

- exact parent-scoped \`special_filter_query_str\`;
- folder-only \`item_type\` and unmodified chain of opaque page tokens;
- explicit terminal \`next_page_token:null\` after normalized provider return;
- matching item name, MIME type, exact parent IDs and unique item IDs;
- no skipped pages, repeated tokens or duplicates.

Possible decisions:
1. \`EXISTING_FOLDER_CANDIDATE_METADATA_READ_REQUIRED\`: one folder found,
   requires separate metadata confirmation before reuse.
2. \`BLOCKED_DUPLICATE_EXISTING_FOLDERS\`: several same-name folder IDs,
   never arbitrate or delete automatically.
3. \`BLOCKED_ABSENT_IN_FOLDER_ONLY_SCAN\`: no folder found, but cannot rule out
   file/type collision. **NEVER CREATE** based on this result.

Every action from this helper has \`create_permitted:false\`, including the
successful existing-folder candidate. The helper validates a supplied
transcript but **cannot independently authenticate** it. Provider transcripts
should be generated by the real connected action, not invented by a model.
If the tool omits \`next_page_token\` on a terminal page, the host may normalize
the schema-defined nullable field to null only when this is the actual result
of that response; absence must never be used to fake an unobserved page.

The helper is an optional diagnostics interface. Merely merging it into the
repository does not automatically wire it to the running ChatGPT Skill.

## F6 remaining acceptance criteria

1. Authorized executor for the separate official Drive v3 scanner runs
   a **complete all-MIME** direct-parent listing with authoritative pagination.
2. A pre-provisioned private audit file stores the journal and returns
   independent downloadable readback bytes with matching SHA-256.
3. A separately retained trusted journal hash is available across session
   changes; missing or older journal must fail closed.
4. One isolated synthetic create attempt after journal readback only; fault
   injection demonstrates errors with and without side effects.
5. Actual live resume must preserve and reconcile the same remote ID with no
   blind retries; concurrency assumptions and limitations reported.
6. The owner reviews changes and authorizes any merge or release separately.
